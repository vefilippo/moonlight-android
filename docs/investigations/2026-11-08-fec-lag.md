# Stream lag on the Chromecast with Google TV: FEC matrix setup (2026-11-08)

## Symptom

On a Chromecast with Google TV 4K (Amlogic S905D3G, 4x Cortex-A55, 2 GB RAM, armeabi-v7a
userspace), streaming 1080p60 HEVC at 35 Mbps from Apollo became laggy after a while. The
stats overlay showed:

| Overlay line | Value when laggy |
|---|---|
| Incoming frame rate from the network | 0.49 FPS (stream at 60) |
| Frames dropped by your network connection | 93-99 % |
| Bandwidth | 12-17 Mbps, so data was still arriving |
| Average network latency | 1-3 ms |
| Average decode time | 4.75-6.4 ms |

It recovered on its own after seconds to minutes, usually when the scene got simpler. It
happened more often with microphone streaming on.

## How it was measured

Everything below was captured on the dongle over wireless adb with the debug build.

- **Kernel UDP counters.** `/proc/net/snmp` (`RcvbufErrors`) and the `drops` column of
  `/proc/net/udp` for the app's uid. The "network" drops were the kernel discarding packets
  because the **video socket's receive queue was full** (`rx_queue` pinned at ~0x80800). The
  packets had reached the device.
- **Wi-Fi state.** `dumpsys wifi`: 5 GHz, RSSI -16 dBm, 866 Mbps RX link, low-latency Wi-Fi lock
  held, no scans or roams at the drop times. Wi-Fi was not the cause (see the limits section
  for one separate event).
- **Ruled out on the way.** Thermals (44-64 C, thermal status 0), memory pressure (no
  low-memory kills; swap full but MemAvailable ~500 MB), GC pauses (1-14 ms, not aligned
  with the drops), and decoder back-pressure (`Dequeue input buffer ran long` absent during
  most drop episodes). The microphone was a contributing factor, not the switch: a mic-off
  session also overflowed, only less often.
- **Per-thread CPU.** A sampler running on the device (`nohup`, so it survived adb drops)
  logged `top -H` for the app every second. During an episode one thread, the native video
  receive thread, sat at **85-93 % of one core** while the other cores were mostly idle.
- **Profile.** `simpleperf record -p <pid> -e cpu-clock -g`, run through `run-as` because the
  device has no hardware PMU. 79 % of the receive thread's samples were in
  `libmoonlight-core.so`. `llvm-addr2line` on the unstripped library resolved the hot
  addresses to `multiply1()` in `moonlight-common-c/reedsolomon/rs.c`, called from
  `reed_solomon_new()`.

## Root cause

`RtpVideoQueue.c` calls `reed_solomon_new(dataShards, parityShards)` for **every FEC block it
recovers**. `reed_solomon_new()` built its encoding matrix as `vm * inv(top)`, where `vm` is
`[I; 0]` and `top` is its top square, the identity. The product is just `vm`, but computing it
costs `shards * data_shards^2` Galois-field multiplies: about 11 million for a 210+40 block,
**124 ms** on the dongle. A 60 FPS frame has 16.7 ms.

That turns any packet loss into a spiral:

1. A few packets are lost and the frame needs FEC recovery.
2. FEC setup takes about 124 ms per block, so the receive thread stops reading the socket.
3. The 256 KB socket buffer overflows and more packets are lost.
4. The client requests an IDR frame. The IDR is the largest frame (3-4 FEC blocks of
   ~200 shards each), it arrives as a burst into the full socket, and it is lost too.
5. The client keeps requesting IDR frames (`Reached consecutive drop limit`). The stream stays
   near 0.5 FPS until the bitrate falls enough for the thread to catch up.

The microphone threads (Opus encoding, capture) take CPU from the receive thread, so the
spiral started sooner with the mic on.

## Fix

moonlight-common-c `eecd540`: build the matrix directly as the identity rows followed by the
existing Cauchy parity rows. The `multiply1()` helper and the temporary `vm`/`top` matrices
are removed.

Verified on the dongle with a standalone test built with the NDK for armeabi-v7a:

| Check | Result |
|---|---|
| Matrix equal to the old construction | 14362 (data, parity) shapes, 0 mismatches |
| Encode + reconstruct with `parity` erasures | ok for 4+2, 32+8, 120+30, 210+40, 200+55 |
| `reed_solomon_new(210, 40)` | 123.7 ms before, 0.035 ms after |

In a 4-minute stream afterwards with the mic on, FEC recovered 3245 frames, the receive thread
peaked at 46 % of a core, and the 0.5 FPS loop did not occur.

## Remaining limits

- **Socket buffer.** `net.core.rmem_max` is 256 KB on the dongle and an app cannot raise it
  without root. A burst well above the stream rate (one was ~10,000 packets/s, about 5x
  normal) can still overflow it. That causes a short hiccup of a few seconds that recovers
  on its own. A lower bitrate (for example 25 Mbps) makes it rarer.
- **Wi-Fi channel changes.** The dongle once moved from channel 108 (5540 MHz, a DFS channel)
  to channel 36 on a different BSSID of the same router. That causes a brief freeze and
  turns off wireless debugging. A fixed 5 GHz channel outside the DFS range (36-48) on the
  router avoids it.

## Reusable debugging notes

- The overlay's "frames dropped by your network connection" counts frames lost **anywhere
  before decode**, including socket overflow on the client. Check the `drops` column of
  `/proc/net/udp` before blaming the network.
- Run long-lived samplers on the device with `nohup` and pull their output afterwards. Wireless
  adb drops whenever the dongle changes access point.
- simpleperf without a hardware PMU: `run-as <package> simpleperf record -p <pid> -e cpu-clock
  -g -o /data/data/<package>/perf.data`, then resolve addresses with the NDK's
  `llvm-addr2line` against
  `app/build/intermediates/merged_native_libs/<variant>/.../libmoonlight-core.so`.
